# 학습 흐름 개선과 확인 방법

## 직접 확인

개발 서버가 실행 중이면 http://localhost:3000 에서 확인합니다. 운영 사이트에는 배포 후 반영됩니다.

이미 오늘의 문제가 완료로 보이면 시크릿 창에서 열어 처음부터 테스트할 수 있습니다. 검증 중 만든 기록은 일반 창의 이 브라우저에 남아 있을 수 있습니다.

1. `/practice/word/step1`: 한 낱말에 `오답`을 입력하고 지운 뒤 정답으로 수정합니다. 나머지 9개는 정확하게 입력합니다. 결과의 **첫 입력 정확도는 90%**, 수정한 낱말은 1개여야 합니다. 조합 중인 정상 한글은 오타로 세지 않습니다.
2. 결과의 **단계 선택으로 돌아가기**를 누르면 다섯 단계 목록이 나와야 합니다. 같은 단계가 자동 재시작되면 안 됩니다. 연습 중 Esc도 같은 동작입니다.
3. `/`: 타자 실력 키우기, 지식 외우기, 좋은 글 필사하기 버튼과 1분 테스트·게임 링크를 확인합니다.
4. `/journey/daily`: 첫 문제에 오답을 제출하고 힌트를 봅니다. 새로고침해도 문제·입력값·힌트가 유지되어야 합니다. 정답을 입력한 뒤 Enter 또는 정답 확인으로 이동합니다.
5. 두 문제를 마치고 홈으로 이동합니다. 최근 활동 이어하기에서 오늘의 지식타자를 열면 세 번째 문제로 이어져야 합니다.
6. 다섯 문제를 마치면 혼자 맞힌 문제 수와 각 정답·설명이 나옵니다. 힌트를 보거나 오답을 제출한 문제는 혼자 맞힌 개수에 포함되지 않습니다. 같은 날 새로고침해도 완료 결과가 유지됩니다.
7. 다음 한국 날짜에 다시 방문하면 틀리거나 힌트를 본 문제가 복습에 우선 배정됩니다. 정답만 맞힌 문제는 3일, 6일, 9일… 최대 14일 간격으로 복습합니다. 하루 복습 대상이 5개보다 많으면 오래 밀린 문제부터 배정합니다.

오늘의 학습 기록은 비로그인용과 로그인 계정별로 분리해 이 브라우저에 저장합니다. 아래 SQL 적용 후 로그인 사용자의 풀이·복습 상태를 기기 간 동기화합니다. 입력 중인 글자는 브라우저에만 보관하며 서버로 전송하지 않습니다. 기존 필사·일반 지식여정 저장 방식은 이번 변경의 대상이 아닙니다.

## 추가 SQL 적용과 새 기능 확인

1. Supabase에서 한글타자왕 프로젝트 `lxvbibfmvsrdstwwlkdm`을 선택합니다.
2. `supabase/daily_journey_progress.sql`은 로컬 전용이며 Git에 포함하지 않습니다. 사용자가 이미 적용했고 실서버의 테이블과 본인 전용 정책을 확인했습니다. 다시 실행할 필요가 없습니다. 새 환경에서는 별도로 전달받은 SQL을 한 번 적용합니다.
3. 새 테이블 하나와 그 테이블의 권한만 생성합니다. 기존 테이블/데이터/정책을 수정하지 않습니다. 이름이 이미 존재하면 전체 트랜잭션이 중단되므로 임의로 DROP하지 말고 오류를 확인합니다.
4. 코드 배포 후 `/journey/daily`에서 로그인하고 한 문제를 풉니다. 저장 중 안내가 사라진 뒤 다른 기기에서 같은 계정으로 열면 진도가 이어져야 합니다. SQL 적용 전에는 동기화 실패 안내가 나오지만 브라우저 저장으로 계속 풀 수 있습니다.
5. 다른 계정으로 바꾸면 앞 계정의 오늘의 문제가 이어지지 않아야 합니다. 비로그인 기록은 자동으로 가져오지 않으며, 명시적으로 가져오기 버튼을 누른 경우에만 병합합니다. 비로그인 원본은 삭제하지 않습니다.
6. 국기·국가명, 원소기호·원자번호, 조선 왕의 순서·재위 기간을 확인합니다. 틀린 답과 힌트 사용 후 새로고침해도 해당 상태가 유지됩니다.
7. `/challenge`에서 **최근 7일 인기 필사** 상위 3개, 완주 인원, 한국 시간 집계 시각과 상세 이동을 확인합니다. 집계 시각 직전 7×24시간의 로그인 사용자별 완주를 글마다 중복 제거합니다. 동률은 최근 완주, 그다음 글 ID 순입니다. 신고 10회 이상·삭제 글은 제외하며 최신 200개 글에 한정하지 않습니다. 기록이 없거나 조회가 실패하면 각각 별도의 안내가 나옵니다. 기존 누적 인기순/도전순 버튼은 그대로입니다.
8. 페이지 소스 보기에서 `/journey/daily`의 h1, 설명, 예시, 코스 링크 3개가 JavaScript 실행 없이 존재하는지 확인합니다. 배포 후 Search Console URL 검사로 실제 크롤링 결과를 별도 확인합니다.

동기화는 페이지 진입과 풀이 체크포인트(정답 확인/힌트, 750ms 묶음)에 수행합니다. 사용자별 최신 상태 한 행만 유지하며 분석 이벤트를 DB에 저장하지 않습니다. 동시 저장은 revision 비교와 최대 3회 병합 재시도로 충돌을 처리하고, 실패 시 로컬 기록과 재시도 버튼을 남깁니다. 자동 실시간 구독은 사용하지 않습니다.

추가 검증: 실제 읽기 전용 연결로 기존 테이블 구조 확인. 임시 PGlite PostgreSQL에서 SQL 생성, 본인 읽기/쓰기, 타 계정 및 비로그인 차단, 삭제 권한 없음, 잘못된 JSON 차단, 기존 테이블 보존, 재실행 충돌 시 원본 보존을 확인했습니다. `tests/daily-sql.mjs`는 PGlite가 설치된 환경에서 실행하거나 `TAJAWANG_PGLITE_PATH`로 모듈 경로를 지정합니다. PGlite는 검증용 임시 디렉터리에만 설치했으며 서비스 의존성은 추가하지 않았습니다.

주간 인기에는 추가 SQL, 새 테이블, 새 분석 서버가 필요하지 않습니다. 기존 공개 기록을 서버에서 500건씩 ID 커서로 끝까지 조회하며 한 페이지라도 실패하면 부분 순위를 공개하지 않습니다. 원본 사용자 ID는 클라이언트에 전달하지 않습니다. 완성된 페이지를 기존 Cloudflare R2/OpenNext ISR 구성으로 캐시하고 1시간 경과 후 방문 시 재생성합니다. 개발 서버에서는 이 캐시가 적용되지 않습니다. 기록량이 크게 증가하면 날짜 인덱스와 DB 내 집계로 전환을 검토합니다.

원격 GTM/GA4 관리자 설정은 변경하지 않았으며 실제 GA4 수집 여부는 별도 확인이 필요합니다.

## 계측 기준

GTM dataLayer에 다음 공통 이벤트를 전송합니다. 원래의 `pilsa_*`, `journey_*`, `speed_test_*` 이벤트는 기존 연동을 위해 유지합니다. **공통 이벤트와 기존 이벤트를 합산하지 않습니다.**

| 이벤트 | 의미 |
| --- | --- |
| `activity_view` | 홈·연습·테스트·필사·지식타자·게임 경로 방문 |
| `activity_input` | 해당 경로 방문 후 첫 번째 비어 있지 않은 입력. 입력 내용은 전송하지 않음 |
| `activity_start` | 활동 시작. 게임·기존 지식여정은 시작 버튼, 연습·테스트는 첫 입력, 오늘의 5문제는 첫 입력/힌트 |
| `activity_complete` | 활동 완료. 짧은 글은 한 문장, 낱말은 한 단계, 오늘의 문제는 다섯 문제, 게임은 게임 종료 |
| `activity_next` | 다른 활동으로 가는 내부 링크 클릭 또는 낱말 결과의 단계 선택 |

`mode`, `path`, `visitor_id`를 공통 분석 기준으로 사용합니다. 화면 방문·첫 입력은 방문 단위, 시작·완료는 활동 단위이므로 단순 전체 건수 비율을 서로 나누지 않습니다. 시작한 사용자 중 완료한 사용자의 비율과 방문한 사용자 중 입력한 사용자의 비율을 각각 봅니다. 다음날 재방문은 방문 날짜별 `visitor_id` 코호트로 계산합니다.

개발자 도구 Console에서 `window.dataLayer.filter(e => e.event === 'activity_complete')`로 확인할 수 있습니다. GTM이 로드되지 않아도 이벤트는 배열에 남습니다. GA4 수집에는 GTM 맞춤 이벤트 트리거·태그 및 매개변수 연결이 필요하며, 이번 코드 변경은 원격 GTM 설정을 수정하지 않습니다.

점수 등급은 정확도 90% 미만이면 D급, 90~94%이면 최대 B급, 95% 이상이면 기존 타수 구간을 적용합니다. 이 기준은 새로 계산한 결과에 적용되며 과거 저장 기록은 수정하지 않습니다.
